# 実時間ベンチマークの条件（v1.3.0）

この拡張機能は、数値の観測状態を与えたモデルとAPI通信を合わせた実時間ゲーム制御を評価します。ゲームを停止して応答を待つ方式はありません。画像認識は拡張機能が担当します。モデル単体の物理推論の正答率を示すものではありません。

## 方式をそろえる

| 方式 | モデルの選択 | 拡張機能の役割 |
|---|---|---|
| v1.1.0 通過位置＋ローカル制御 | 上寄り／中央／下寄り | 状態を見てクリックを決定 |
| `jev` 従来方式 | click／wait | 応答時にクリック、次の応答まで待機 |
| `jev-plan` 予定方式（実験） | 固定された16個のクリック予定 | 選ばれた予定を時刻どおり実行 |

この3方式は異なる制御能力を測ります。予定方式と従来方式を同じモデルで比べるときは「制御方式の比較」として記載してください。異なるモデルの比較には同じ方式を使います。旧版と新版、異なる質問の版を混ぜた単一ランキングは作りません。

## 固定のクリック予定

800msの区間について、応答受信から0・200・400・600msの4時点でクリックするかどうかを組み合わせた16候補を、1つのChoice質問へ常にすべて提示します。空の予定は800ms入力なしです。候補を状態に応じて選別したり、候補の軌道や衝突判定を計算してモデルへ渡したりはしません。

0msのクリックは次の描画フレームで実行します。予定開始から400ms経過後の最初のフレームで次の問い合わせを送り、旧予定の実行を続けます。同時に実行するAPI要求は1件です。クリックしたフレームで新規要求を送ると観測がクリック前になるため、その場合は次フレームで要求します。

予定切れは、次の応答が未到着のまま800msの予定が終了した回数です。API上限で最後の予定を正常に終えた場合は、予定切れへ数えません。死亡・停止で破棄したクリックは `terminated_clicks`、次の予定で置き換えたクリックは `superseded_clicks` として分けます。

新しい応答が到着したら未実行の旧クリックを破棄し、受信時刻を基準に新しい予定を開始します。計画が尽きた場合は新しい応答が来るまで入力しません。`wait_all` による無操作は有効な予定で、予定切れとは区別します。開始操作は元ゲームの標準開始／再挑戦操作です。最初の推論が遅い場合もゲームは進み、開始時の無予定時間を記録します。

ローカルで危険を見て操作を補正したり、信頼度で選択を変更したりはしません。停止・死亡・非表示・リサイズ・APIエラーで未実行の予定を破棄します。描画の停滞で実行期限から50ms以上遅れたクリックは追いかけて連打せず、実行漏れとして記録します。従来方式の900ms応答停止は予定方式に適用せず、予定方式では2500msのAPIタイムアウトまで通信待ちも成績に含めます。

800ms・200ms刻み・400ms後の再要求は、v1.3.0で固定した実験条件です。最適な長さや、得点が改善することを確認した値ではありません。16候補の選択でも、未来の運動を判断する負担は残ります。[Choiceの公式仕様](https://docs.typesafe.ai/primitives/choice)は固定候補の選択に対応していますが、[Jev 1.13の公式制約](https://docs.typesafe.ai/model-jaggedness/jev-1.13)には数値精度や多段階の推論が弱点として記載されています。

## モデルへの入力

- 観測した位置、推定速度、半径、上下壁、次とその次の障害物。
- ゲームの重力、ジャンプ後の速度、障害物速度、フレーム時間上限、当たり判定のルール。
- 実測から推定した通信時間、観測からの経過時間。
- 予定方式では、すでにJevが選択済みの未実行クリック時刻と、現在の予定の残り時間。時刻は今回の観測を基準にした相対値。

未来位置・軌道・衝突するかどうか・安全余裕・推奨操作は送信しません。従来方式の固定10例は従来のclick/wait質問だけに残します。予定方式に対応する正答例は今回追加していません。入力の形式と例の有無も比較条件です。

## 採取と比較

1. 拡張機能の版、プレイ方法、質問のSHA-256、画面・Canvas寸法、ブラウザ、API上限、自動再挑戦の設定をそろえます。
2. モデルIDは可能なら版を固定します。`jev-latest` などのエイリアスでは重みが変わる可能性があるため、ログに返された実モデルIDも記録します。
3. 画面を表示したまま、ゲームへ手動入力せずに複数回プレイします。比較するモデルを交互に実行し、開始回数と終了条件を事前にそろえてください。
4. 終了後の応答待ちが終わり「ログをコピー」が有効になったら、1回の「開始」につき最後のログを1ファイル保存します。途中のログと最終ログを二重に数えません。
5. 0点・最初の応答前の死亡・通信エラーも結果に含めます。API上限や手動停止で打ち切った試行は、自然な死亡と分けて表示します。

ログには質問本文とハッシュ、制御条件、要求時の状態、応答時の直近観測、モデルの選択、確率、得点、生存時間、API所要時間、選んだ／実行したクリック数、置換されたクリック数、50msを超えて実行できなかったクリック数、予定切れ回数・無予定時間、検出した手動入力を含めます。手動入力の検出はゲーム枠内のpointerdownとSpace／ArrowUp／Enterです。改造されたページや外部ツールの入力すべてを検出するものではありません。

詳細イベントは直近2400件を保持し、古い記録を削除した場合は `truncated` を立てます。v1.3.0の累積集計は古いイベントを削除しても残ります。生存時間は実時計で測り、死亡の検出は描画フレーム単位です。API遅延の分布には死亡後に届いた成功応答も含め、タイムアウト・エラー数は別に表示します。APIキー・画像・API応答本文は記録しません。

## ログの集計

Node.jsで保存済みログを集計できます。通信や追加のモデル要求は行いません。

```sh
node tools/summarize-logs.mjs log1.json log2.json > summary.json
```

`condition_sha256` が同じ行で制御条件・入力条件・画面環境が一致します。接続先と要求／実応答モデルは行ごとに分けます。各行には全スコア、中央値・平均、生存時間中央値、API p50／p95、死亡後の応答、判断頻度、行動分布、予定切れ等が出ます。通信エラーや上限停止による打ち切りは `stopped_games` に残します。動作中・手動入力あり・ローカル制御のログは集計から除外し、理由を出します。v1.3.0より前のログは比較条件が足りないため除外します。

障害物は元ゲームの `Math.random()` で生成され、同じ障害物列を保証できません。同じ条件でも通信と描画時間が変わります。複数試行のばらつきを含めて評価してください。予定切れが多ければ通信の影響を示唆しますが、それだけで死亡原因を断定できません。入力の推定誤差、モデル判断、限られた行動候補も結果へ影響します。

## 実装の確認範囲

公開ゲームの入力イベント・物理定数・更新順序と、ChoiceのAPI仕様を確認して実装しています。v1.3.0ではJavaScript構文・差分・配布JSONの形式のみ確認し、自動テスト、実API接続、更新後のChrome実プレイは行っていません。改善効果の実測結果はまだありません。
